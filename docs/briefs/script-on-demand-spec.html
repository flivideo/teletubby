Script on demand, between takes

An agent can already write a short segment in your voice and put it on the prompter, but only from the video's Knowledge. This adds two ways to ask for a script while you're recording: fill-in for something new, and rescue for the bit you keep stumbling on.

Sample: D07, Buzz coding teamSize: ~75–90 min for one coderStatus: spec only, not built

Where it hurts

1Six goes at one lineYou stumble through the same piece again and again. What you want is a clean script of what you were trying to say.
2Incoming is silentToday: takes in Incoming aren't transcribed. FliHub only transcribes a take once it lands, so an agent can't read your attempts.
3The writer reads only KnowledgeToday: segment-writer reads dossiers and notes, never what you've actually said, so it can't build on it.

What you'd see

Between takes you type one line to the agent. A minute later the script is on the prompter. Teletubby itself doesn't change; the work is in FliHub (quick transcripts for Incoming) and in the writing skill (two modes).

The spec

What the job is

Quick transcriptsEach take in Incoming gets a fast transcript from FliTools pass 1 (Groq or mlx-whisper), not CrisperWhisper
Agent can read themA FliHub verb lists Incoming takes with their quick text, newest first
Rescue modeReads the Incoming takes you name (default: the latest run) plus Knowledge. Writes what you were trying to say. Loads as a new version beside the stuck segment
Fill-in modeReads kept takes so far, in chapter order, plus Knowledge. Writes something you haven't said. Loads as the next segment
Never readsTrash. Those takes were rejected after ingestion
LoadingSame as today: script.create → write_transcript → write_trigger_set, dry run first

Done-check

proofFliHub test: a file dropped in Incoming gets a quick transcript and shows in the new verb. Skill run (isolated Teletubby): rescue from three fixture takes and fill-in from two kept takes each load a script
test_auditdev-team:audit-test-quality on the new tests
before_afterIncoming without and with quick transcripts; the prompter before and after a rescue
durationFrom the queue timestamps

Out of scope

  • Asking by hotkey or voice while recording. You ask the agent between takes.
  • FliHub guessing when you're stuck. You decide when to ask.
  • Changes to Teletubby itself.

What I checked, and what I didn't

  • FliHub queues a transcript only when a take lands: flihub/server/src/utils/renameRecording.ts:268-277, sent to FliTools POST /api/transcribe (flihub/server/src/utils/flitoolsClient.ts:94).
  • FliTools has a fast pass (groq-whisper, mlx-whisper) and an edit-grade pass: fli-core/src/brand-settings.ts:15-17.
  • How a script gets onto the prompter today: appydave-plugins/flivideo/skills/segment-writer/SKILL.md §4.
  • Not checked: whether FliTools can be asked for pass 1 only on a single file. If it can't, the job grows by a FliTools change.
  • Not checked: Groq pacing. A busy recording morning could queue many quick jobs; Captain's Log has hit Groq's limit before.

Choices for David

When Incoming takes get transcribed

Every take as it arrives, or only when you ask for a rescue.

As it arrives. Then the script comes back in under a minute when you ask, which is the whole point mid-recording.

Where the quick transcripts live

Next to the take in ~/ecamm, or in a FliHub cache folder.

A FliHub cache folder. ~/ecamm stays Ecamm's, and the quick transcript is thrown away when the take lands and gets its full one.

Rescue: replace the stuck segment, or sit beside it

Overwrite the script you were reading, or add it as v2 next to v1.

Beside it, as mocked. You can flip back if the rescue lost something you liked.
